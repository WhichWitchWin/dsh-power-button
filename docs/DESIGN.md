```
拖动 → 贴边收起 → 鼠标移上去展开 → 点击 → （有任务在跑才二次确认）→ 重启 或 退出
```

## 它解决什么问题

DSH 桌面版没有界内重启入口。托盘菜单和「应用」菜单里的重启只在开发构建下出现
（`main.js:11941` 的 `...development ? [` 分支，其 `app.relaunch()` 在 `main.js:11952`），
发布版只能先退出再从开始菜单重新打开。

## 为什么必须这么做

桌面版的重启由 Electron 主进程持有：`app.relaunch()` + `app.quit()`
（`main.js:11027`）。但主进程没有把这条能力开给插件——`preload-app.cjs` 只暴露了
`browser` / `deviceInfo` / `keyboard` / `shortcuts` / `updates`，没有任何
restart 或 quit 通道。所以插件不能"请求"重启，只能从外部**复刻**它。

而复刻有个先有鸡还是先有蛋的约束：DSH 宿主进程是 Electron 主进程的 IPC 子进程
（`main.js:3674`），杀掉主进程就会连带杀掉宿主——也就是说，下杀手的那段代码
不能待在宿主进程里。因此本插件把工作交给一个**脱离进程树**的 PowerShell 辅助进程。

### 为什么不用 `ctx.appExit`

宿主上下文里确实有 `ctx.appExit`（官方文档：*"Launcher facts, not config.
`cmdlineArgs` 和 `appExit` 由 launcher 在树挂载前提供"*，实现在官方的
`@deepseek-ai/dsh-cmdline`）。**第三方**插件 `dsh-system-control`
（`FrankZhangIronly/dsh-system-control`，**不是官方项目**）正是用它 +「退出码 42」实现重启的，
但它面向 `dsh web` 终端形态：**那条退出码契约属于它自己的启动器 `DSH Web.ps1`，
桌面版的启动器是 `dsh-desktop-host`，契约不存在。**

实测（静态取证，未真的调用）：

```
main.js:3722  child.once("close", (code) => {
main.js:3724    if (code !== 0 && code !== null) this.fail(`dsh desktop host exited with ${code}`)
main.js:3725    else this.fail(`dsh desktop host stopped`)      ← code === 0 也走这里
main.js:3813  if (!this.failureReported && !this.stopping) this.onFailure?.(error)
main.js:3793  async stop(...) { this.stopping = true }          ← 只有壳自己拆卸时才豁免
main.js:11051 function reportFatal(...) { recovery.report(...) } ← 崩溃报告界面
```

宿主进程一 `close`，**无论退出码是 0 还是 42，都调用同一个 `fail()`**；唯一的免死金牌
`this.stopping` 只在壳主动 `stop()` 时置位。所以桌面端的 `appExit(0)` 不是"干净退出"，
`appExit(42)` 也不是"重启"——**两者都会弹出致命错误界面**。合法方向是反过来的：
壳 → 宿主 `child.send({type:"shutdown"})`（`main.js:3795`），只有壳能发。

因此 `quit` 仍走 `taskkill`：不是因为它优雅，而是因为这个壳里**没有更优雅的路**。

## 工作流程

```
点击「重启 DSH」→ （有任务在跑才二次确认）
      ↓
宿主半 POST /api/dsh-restart/action { action: "restart" }
      ↓
宿主半同步等待 lib/restart-helper.ps1 的「引导阶段」返回
      ↓
引导阶段用 Win32_Process.Create (WMI) 重建自己为「工作阶段」，然后退出
      ↓
工作进程（父进程是 WmiPrvSE，不在应用进程树里，taskkill 够不到它）：
  1. 记下起始时刻，算出 settleMs 的「截止时刻」
  2. 趁主进程还活着，读它自己的命令行  ← 复刻 app.relaunch() 的语义
  3. 趁宿主还活着，问出它监听的端口**和绑定的地址**
  4. 只补睡「截止时刻之前还剩的时间」，再 taskkill /PID <主进程> /T /F
  5. 等三个条件同时成立：主进程消失、宿主消失、端口释放
  6. 用步骤 2 记下的命令行重新拉起
  7. 轮询新实例的窗口并置前（见「新窗口置前」一节）
```

第 1 步与第 4 步之间是**一个截止时刻，不是一次固定睡眠**。需要保证的性质是
「worker 启动到杀掉 shell 之间至少经过 settleMs」，而步骤 2、3 全是只读的，可以让它们
与这段时间重叠；原来的写法先睡满 settleMs 再去做识别，两者相加，每次重启都白等一段。
识别本身实测：路径读 ~90ms、端口发现（netstat）~13ms，都远低于默认的 500ms。

**端口释放这一项曾经白等约 2 秒——原因在判定手法，不在操作系统。** 早先用
`TcpClient.Connect` 判定"没人监听了"，而只有 REFUSED 才算释放。实测（本机）：
连一个**从未被监听**的端口，也要 **~2040ms** 才返回；连一个刚死掉的监听者同样 ~2036ms。
也就是说那 2 秒是**探测自身的 TCP 超时**，不是端口真的被占。日志里那句
`shell/host 已消失` 到 `三者释放` 之间的空档就是它。

改成**bind 该地址**后：端口一释放立刻成功（实测 **27–32ms**，日志新增
`port <n> released after <ms>ms` 一行便于回归观察）。click → relaunch 实测
由 ~4.0s 降到 ~2.2s。

> bind 有一个**方向性**风险，必须按原地址 bind 才安全。实测四种组合：
> 监听在 `127.0.0.1`、bind `127.0.0.1` → 失败（正确判为"仍占用"）；
> 监听在 `0.0.0.0`、bind `0.0.0.0` → 失败（正确）；
> **监听在 `0.0.0.0`、bind `127.0.0.1` → 成功（误判为"已释放"）**；
> 监听在 `0.0.0.0`、bind `::` 同样成功（误判）。
> 所以端口发现必须把地址一起带回，再用同一地址判定；地址未知时（调用方直接
> 传 `-WebPort`）退回 connect 判定，宁可慢也不误判。bind 失败的方向是安全的：
> 判为"仍占用"→ 等满超时后带 WARNING 继续，慢但正确。
>
> **交叉地址必然误报，这抬高了"发现到正确地址"的重要性**：它是这条安全性质的
> **唯一**防线，所以端口发现那节的两个覆盖缺口（IPv6、回环白名单）不是小问题。
>
> 另一条实测纠正：`TIME_WAIT` **不会**让同地址 bind 失败。曾有一条注释
> 断言它会（"慢但正确"），实测相反——制造出真实 `TIME_WAIT`（两端都关、netstat
> 确认）后同端口 bind **成功**。所以这里不存在"用正确性换速度"的取舍，是**又快又对**；
> 那条会误导后人回退改动的注释已删。真会粘住 bind 的是防火墙之类，方向仍是安全的。

「退出 DSH」走同一条链路，只是跳过步骤 2、5、6、7——只杀，不再拉起。

界面在动作期间显示"正在重启 DSH…"，超时上限 40 秒：真正耗时的是 powershell.exe 冷启动
（实测单次 ~155ms，需两次）与新实例自身的启动那段，而这个动作不可撤销，误报失败比多等
几秒糟糕得多。

每一步都追加到 `$DSH_HOME\logs\restart-button.log`。

日志目录由宿主半在**启动时**算好并作为参数交给辅助进程（工作进程不继承环境，自己算不出来）。
宿主半先看 `DSH_HOME` 环境变量，没有就从自己的启动参数里**按形状**找出 profile 目录
（`<某个路径>\profiles\<名字>`），再往上一级得到 `$DSH_HOME`。

> 这里曾经写死取 `argv[2]`，而桌面版的启动参数是
> `<entry> <dshRoot> <profileDir> <runtime> …`——**profile 是 `argv[3]`**。
> 取错一位正好指向 `app.asar`（一个**文件**），于是 `mkdirSync` 抛错被静默吞掉，
> 日志落到 `%TEMP%`、界面开关也永远不落盘。现在按形状匹配，启动器再插参数（开发构建
> 会插 `--inspect`）也不会错位。

### 为什么等三个条件而不是睡一个固定值

第 5 步最初是 `Start-Sleep -Milliseconds 800`——一个**猜出来的**经验值，两个方向都可能错：
太短会撞上单实例交接，太长则每次重启都白白慢一截。

单实例交接是这里的真正杀手，而且它**从外面看不出来**：新的那份把焦点交给将死的旧的，
然后自己退出——用户看到的是"什么都没发生"。所以插件等的不是时间，而是这个结局的
可观测前兆：

| 条件 | 为什么它是前兆 |
| --- | --- |
| 主进程消失 | 单实例锁由它持有 |
| 宿主进程消失 | 否则可能留下两个宿主抢同一个端口 |
| 端口释放 | 端口被占就是"新进程会自撞"的直接证据 |

端口在步骤 3 问出（`netstat -ano`，`Get-NetTCPConnection` 兜底）——宿主
启动时只收到 profile 目录，**不会告诉子进程自己选了哪个端口**。等待整体受
`waitForExitSeconds` 约束；超时**不算失败**，但会在日志里写明是哪个条件没满足，
这样一次失败能自己说出原因，而不是留给人去猜。

> 两条发现路径的顺序与判定手法都是实测决定的，不是偏好：
> 首调 `Get-NetTCPConnection` 实测 700–900ms（模块导入），`netstat` 只要 ~13ms，
> 所以 netstat 在前、cmdlet 兜底；而"端口是否释放"必须 **bind 同一个地址**，
> 理由见上一节。

#### 端口发现必须覆盖 IPv6（一次真实缺陷）

初版写的是 `netstat -ano -p TCP`。看着更精确，实际是错的：**协议选择器是互斥的**
（`netstat /?` 把 `TCP | UDP | TCPv6 | UDPv6` 列为四个并列选项）。本机实测：

| 命令 | 行数 | 含 `[` 的 IPv6 行 |
| --- | --- | --- |
| `netstat -ano -p TCP` | 344 | **0** |
| `netstat -ano` | 434 | **29** |
| 耗时 | ~13ms | ~13ms |

代价为零，覆盖却完全不同。`[::1]` / `[::]` 正是**双栈 Node 服务**报出来的形式
（`server.listen(port)` 不带 host 时就是这样），所以 `-p TCP` 会让快路径漏掉每一个
IPv6 监听：宿主绑 `::` 时白白退回 700–900ms 的 cmdlet，绑 `::1` 时**干脆找不到**，
端口条件随之整体失效——而这正是"过早重启 / 单实例交接"要防的那个洞。现在改跑
`netstat -ano`，并有一条**禁止性**守卫（断言 `-p TCP` 不出现），而不是只断言新写法。

同一个洞还有第二处在 cmdlet 兜底里：回环白名单原本写死三个字面量
（`127.0.0.1 / 0.0.0.0 / ::`），**漏掉 `::1`**。现在是一个谓词：`127/8` 按**网段**
匹配（`127.x.x.x` 全算，不只 `127.0.0.1`）、显式包含 `::1`、并归一化 IPv4-mapped
形式（`::ffff:127.0.0.1` → `127.0.0.1`）。实测四种绑定（`::1`/`::`/`127.0.0.1`/`0.0.0.0`）
全部正确发现，旧代码在 `::1` 与 `::` 上均返回 `Port=0`。

两条路径还会各自偷偷过滤（netstat 不过滤、cmdlet 过滤三个字面量），且取的是
**netstat 的行序**——实测同一 pid 可命中 7 行（含非回环地址），哪一行胜出没有文档
保证。现在两路都只**收集**候选，由一个排序器统一选：回环优先 → 具体地址优先于
通配 → 端口/地址兜底，因此"发现到哪个地址"不再取决于行序。

### 新窗口置前

**症状**：重启后新窗口不总在最前，会被其它程序挡住。

**为什么必须由辅助进程来做**：新壳是被一个后台进程拉起的，而当时前台属于别的程序；
Windows 只允许**持有前台的进程**把前台权交出去。壳自己启动时抢不到，辅助进程是唯一
还活着、又已经脱离那棵树的角色。

**用哪种手法是实测出来的**，不是选看起来最干净的。全部候选都在**与辅助进程相同的处境**
下测（WMI 创建、无控制台、**不是前台进程**），对象是两个无关窗口，判据是全局顶层窗口
z 序：

| 手法 | 结果 |
| --- | --- |
| `SetForegroundWindow` | z 序不变 |
| `SetForegroundWindow`（先 `AttachThreadInput`） | z 序不变 |
| `SwitchToThisWindow` | z 序不变 |
| `BringWindowToTop` + `SetForegroundWindow` | z 序不变 |
| `SetWindowPos(HWND_TOP)`（带/不带激活） | z 序不变 |
| **`SetWindowPos(HWND_TOPMOST)` → `(HWND_NOTOPMOST)`** | **抬到最前，且保持** |

前五种全是"请求激活"，而前台锁拒绝把前台给一个不持有它的进程——所以它们**在这里**
什么也不做。进一次置顶带、立刻退回普通带只改 z 序，不需要那个权利：这是唯一有效的。
**不要**把这段"清理"成一次 `SetForegroundWindow`，那是实测无效的写法。

配对对照（先强制"被遮盖"状态，两组起点相同）：

| 组 | 处理后 | 2 秒后 |
| --- | --- | --- |
| 不置顶（×2） | 仍在后 | 否 |
| 置顶（×2） | 到最前（z 933→49） | **是** |

**必须轮询到"新窗口出现"再抬，而且不能抬到第一个就收工。** 真实壳的窗口是
`show:false` + `ready-to-show` 才显示的，进程起来时窗口还不存在。第一版实现在
**第一次抬成功后即返回**，实测抬到一个更早出现的窗口就结束了，真正的主窗口从未被抬——
这正是用户看到的现象。现在的写法是每 150ms 扫一遍，**每个"新出现"的窗口各抬一次**，
抬到后静默 3 秒无新窗口才收工，总上限 25 秒。

**"各抬一次"必须是"成功抬过的才不再抬"。** 早先的版本在**调用之前**就把句柄标记为
已处理，于是"一次机会"退化成"一次尝试"：某个 tick 上没抬成功的窗口被永久放弃，循环
只会空转到 25 秒上限。现在只在 `Raise()` 返回真之后才记入，失败的下个 tick 重试。

> 失败分支的可达路径是**实测**出来的，不是推测：`Raise()` 作用在**活着的可见窗口**上
> 返回真，而 `Windows()` 从不吐出已经死掉的句柄（窗口销毁后就不再被枚举）——所以返回假
> 只发生在"枚举到调用之间窗口消失"的**竞态**，那恰好是重启后壳正在翻动启动窗口的时刻。
> 重试上限 40 次，且每个窗口只在**首次**失败时写一行日志，避免 150ms 轮询把日志刷爆。

置前失败**绝不影响重启成功**：整段包在 `try/catch` 里，失败只写一行日志。

### 为什么必须用 WMI 而不是 detached spawn

最初实现用 `spawn(..., { detached: true, stdio: 'ignore' })` + `unref()`。
**实测证明 `detached` 逃不出进程树**：这是本插件最关键的一条约束，因为辅助进程
的职责恰恰是杀掉包含宿主的那棵树。

对照实测结果（Electron-as-node 下，逐项测量）：

| 启动方式 | 能否执行 | 能否逃过对调用者 `taskkill /T` |
| --- | --- | --- |
| `spawn(detached: true, stdio: 'ignore')` | 能 | **不能**——子进程的父进程仍是调用者，被一并终止 |
| `spawn(stdio: 'pipe')`（非 detached） | 能 | 不能 |
| `Win32_Process.Create` (WMI) | 能 | **能**——父进程是 `WmiPrvSE.exe`，已跨创建者退出存活 |

`detached: true` 只新建进程组和控制台，**不改变 `ParentProcessId`**，所以
`taskkill /T` 照样连坐。WMI 创建的子进程父进程是 WMI 服务，才真正脱离应用进程树。

因此改为两阶段：宿主半同步等待一个短命的引导进程返回，由引导进程用 WMI 创建真正的
工作进程。宿主半之所以要**等**引导进程，是因为它的退出码就是「WMI 是否创建成功」的
唯一信号——否则浏览器会显示「正在重启」而实际什么都没启动。

WMI 创建的子进程**不继承调用者的环境**（实测自定义变量与 `DSH_HOME` 均为 `null`，
只得到用户基线环境），所以日志目录等事实由宿主半显式作为参数传入。

### 为什么工作进程的窗口不会闪

工作进程是一个 PowerShell 进程，而它的控制台窗口是**人能看见、也能按 Ctrl+C** 的东西——
把重启杀死在"DSH 已被要求关闭"和"DSH 已被重新拉起"之间，结果是应用停在那里再也不会起来。
所以窗口隐藏了两层，`-WindowStyle Hidden` 只是第二层。

**`-WindowStyle Hidden` 单独不够**，因为 Win32 在进程启动时就创建窗口，早于 PowerShell
解析自己的命令行，那个标志到得太晚。真正起作用的是 WMI 在**创建时**应用的
`Win32_ProcessStartup.ShowWindow = 0`。

实测（轮询 `EnumWindows` 找新 pid 的可见顶层窗口）：

| 启动方式 | 是否闪出可见窗口 |
| --- | --- |
| 只传 `-WindowStyle Hidden` | **会闪** |
| 传 `ShowWindow = 0`（`ProcessStartupInformation`） | **不会**（对照组能观测到窗口） |
| 再叠加 `CreateFlags = CREATE_NO_WINDOW` | `Win32_Process.Create` 返回 **21**（参数无效），被拒，单独或组合都一样 |

所以 `CreateFlags` 故意不设。若某个受限的 WMI 提供程序拒绝了 `ProcessStartupInformation`，
引导阶段会**去掉它重试一次**——窗口可能会闪，但重启仍然完成，不会留给用户一个永远没反应的按钮。

### 为什么不做优雅关闭

`taskkill` 不加 `/F` 会发 `WM_CLOSE`，理论上能让应用走自己的关闭流程。这条路在本
应用中**不可用**：桌面壳拦截了主窗口的 `close` 事件并 `preventDefault()` 隐藏到托盘
（`resources/app/lib/main.js` 的 `window.on("close")`），所以关闭请求只会让窗口消失、
进程照常活着。真正的优雅退出是壳内部的 `app.quit()`，外部进程无法调用。

代价是重启属于强杀，进行中的会话会被硬中断（确认框已提示）。

## 两个界面与它们的开关

| 界面 | 落点 | 槽位 | 关闭开关 |
| --- | --- | --- | --- |
| 悬浮按钮 | 页面任意位置，位置持久化 | 自建 root | `floating` |
| 侧栏电源 | 侧栏底部头像行内、头像左边 | `sidebar.footer.action` | `sidebar` |

侧栏电源在关闭时 `return null` 而不是隐藏：槽位**不预留空间**，`return null` 就是
官方推荐的"我不占用这个位置"。

### 两个界面的收起形态

两个控件都用同一套「收起—鼠标移上去展开」的语义，并且**复用同一组关键帧**
（`dshrb-reveal`），不是各写一份：

| | 收起形态 | 展开触发 |
| --- | --- | --- |
| 悬浮按钮 | 贴左/右边缘的 8×44 细条（**高 = 按钮高**） | 鼠标移上去、菜单打开、或拖拽中 |
| 侧栏电源 | 头像左边的 14px 竖条（图标按钮高） | 鼠标移上去，或菜单打开 |

两条细条**都带一个标记**，这样"收起"状态一眼能看出这里有个开关，而不是一根无名小条。

**标记是一条竖线，不是图标**（用户要求："细条不要图标，就留一个竖线吧"）。之前复用的是缩小版电源
图标，在 8px/14px 宽的条子里虽然能看清但太"忙"，而一根竖线的意思是"这里有一条可打开的控件"，
不必再假装自己是第二个带符号的按钮。实现上：

- 它是**一个普通元素**（`sliverMark()` 返回 `span.dshrb-mark`），不是 SVG —— 一条 2px 的直线
  不需要路径；
- 两条细条共用**同一个函数 + 同一条样式规则**，所以两者不可能分叉；
- 线条用 `background:currentColor` 画，但**颜色是自己声明的**（见下）。

```css
.dshrb-mark{width:2px;height:16px;border-radius:1px;corner-shape:round;
            background:currentColor;opacity:.9;
            color:var(--dsw-alias-label-secondary,#8a8f98)}
```

#### 竖线颜色为什么不能只靠 `currentColor` 继承

一开始线条只写了 `background:currentColor`，想着"自动跟随所在细条的颜色"。**实测证明这在两个
细条上会得到两种颜色**——因为两个控件本身设的 `color` 不同：悬浮条是
`--dsw-alias-label-secondary`，而侧栏按钮是 `color:inherit`，继承的是侧脚区域的正文色。

无头浏览器实测（同一份样式规则，两种宿主语境）：

| | 计算出的线条颜色 |
| --- | --- |
| 悬浮条里的竖线 | `rgb(138, 143, 152)`（浅灰） |
| 侧栏里的竖线 | `rgb(27, 28, 30)`（近黑） |

同一条"表示同一个东西"的竖线，一个浅灰一个近黑——这正是用户要求统一的那种不一致。所以颜色
**显式写在 mark 自己身上**，两个细条在任何主题下都同色。

顺带一个连带问题：既然线条不再继承，那条"悬停变白"的规则（它靠设置**细条**的 `color` 生效）
就够不到线条了，hover 时线条会停在灰上、压在品牌蓝底上反而更弱。因此补了一条
`.dshrb-strip:hover .dshrb-mark,.dshrb-sb[data-rail='true']:hover .dshrb-mark{color:#fff}`。
`check.mjs` 两条守卫：mark 必须自己声明 muted 令牌、必须有 hover 变白规则。

`corner-shape:round` 在这里是**必需**的：2px 宽 + 1px 圆角就是一个全圆（胶囊端）形状，
宿主那条通配 superellipse 会把它两端压方——配对规则见下面的圆角形状一节。实测渲染结果
`2.0×16.0 / radius 1px / corner-shape: superellipse(1)`（= 正圆），配对确实生效。

> 侧栏按钮有**两个**子元素（16px 图标 + 竖线 mark），所以每个状态必须只显示其中一个，否则
> 展开时会同时出现图标和竖线。规则是：`[data-rail='true']` 只显示 mark，其余状态只显示图标。
> 侧栏那条 mark 规则的特异性（3）**必须**高于通用的子元素隐藏规则（2），否则 mark 会在唯一
> 需要它的状态里被藏掉——`check.mjs` 断言了这个比较。

#### 悬浮条的高度必须等于按钮高度

用户报告"条子和按钮宽度不一致"，追问后确认轴是**高度**：条子曾硬编 64px，而按钮是 44px，
所以展开的一瞬间控件会**变一次尺寸**。修法是**删掉长度常量**（原来的 `STRIP_H`），
条子高度直接取 `SIZE`，这样两者在物理上不可能再分叉：

```js
var stripStyle = { top: stripTop + "px", width: STRIP_W + "px", height: SIZE + "px" }
```

宽度仍是唯一的差异轴，这才是"按钮从边缘滑出来"而不是"换了个东西"。

**两者宽度是刻意不同的**，各读自己的常量：悬浮 `STRIP_W = 8`、侧栏
`SIDEBAR_SLIVER_W = 14`。侧栏那条必须更粗才能在视觉上和悬浮条**等重**，因为：

- 它**四边都有 1px 边框**，而悬浮条朝窗外那条是 `none`（`border-box` 下边框会向内
  蚀掉填充宽度）；
- 它的底色压在侧栏自己的近白填充 `neutral-bluish-50`（`#f9fafb`）上，而悬浮条压在
  页面底色上——浅色主题下两点亮度差只有约 4%，**同样像素数看起来更细**。

所以这里**故意不共用常量**：需求就是两者不同，硬套一个数只会互相牵制。

### 圆角形状：跟随 DSH 的全局 superellipse，但全圆形状必须"退出"

DSH 有一条全局样式：`corner-shape.css` 在 `@supports (corner-shape: superellipse(1.5))`
内定义 `--dsw-corner-shape`，**通过通配选择器应用到所有元素**及其 `::before`/`::after`。
所以这个"方一点的圆角"是**房屋风格（house style）**，第三方插件默认就该跟随——本插件的
菜单、行、面板都**故意不声明** `corner-shape`，正是为了继承它。

但官方文档在同一段给了明确例外：

> **Full-round shapes — `border-radius: 50%` circles and pill radii — pair
> `corner-shape: round` with their radius in the owning component sheet because a
> superellipse deforms them.**

即**全圆/胶囊形状必须配对 `corner-shape:round`**，否则会被 superellipse 压成方圆形。
无头 Chromium 154 实测（这就是"拨杆还是不一样"和"圆角不够圆滑"的根因）：

| 形状 | 声明 `corner-shape:round` | 不声明 |
| --- | --- | --- |
| 拨杆轨道（`999px` 胶囊） | `superellipse(1)` = 正圆 | **`superellipse(1.5)`** = 被压方 |
| 圆形按钮（`50%`） | `superellipse(1)` = 正圆 | **`superellipse(1.5)`** = 被压方 |

（`superellipse(1)` 与 `round` 等价。）

所以本插件有**五个**全圆形状必须显式退出：`.dshrb-btn`（圆形按钮）、`.dshrb-sw`
（拨杆轨道）、`.dshrb-swthumb`（拨杆滑杆）、`.dshrb-juice`（按压溅出的小液滴）、
`.dshrb-mark`（细条里那条 2px 竖线——宽 2px 配 1px 圆角就是全圆端）。

> `.dshrb-juice` 与 `.dshrb-mark` 都是**被 `check.mjs` 的配对守卫抓出来的**，不是靠眼看：
> 前者只有 7px、在屏上不到半秒；后者的 `1px` 圆角看上去完全不像"全圆"。守卫的规则有两支：
> ① 任何 `border-radius` 为 `50%`/`999px`/`100px` 的规则，②**任何 `border-radius:1px` 且
> `width:2px` 的规则**（这一支专门为竖线而加，否则它会被漏掉），两支都必须同时声明
> `corner-shape:round`；另一条断言则相反地要求普通面板**不得**声明它（否则就是跟本该继承的
> 房屋风格对着干）。

### 展开是「滑出」不是「跳出」，而且不能有断层

`dshrb-reveal` 分 5 个阻尼落点（0%→26%→48%→70%→86%→100%）渐进收敛，而不是
一个极值弹簧一步到位——后者就是"跳出"的观感来源。两个界面各自由 `transform-origin`
锚在自己贴的那条边（悬浮跟 `data-side`、侧栏固定左缘），这样只有自由边在动。

**动画里刻意不用任何 `translate`**：指针是从**贴边那一侧**进入细条的，任何非锚定的
位移都可能把盒子挪出指针所在像素 → `pointerleave` → 塌陷 → 又落回指针下，重新触发前
面那个闪烁闭环。只做「锚定原点缩放」不会：最小缩放时盒子仍覆盖着细条本身。

#### 「断层」的成因：动画终点 ≠ 悬停静止比例

动画原先 100% 收在 `scale(1,1)`，但 `.dshrb-btn:hover` 画的是 `scale(1.06)`。动画一
结束，`transform` 所有权交还给悬停规则，控件就从 1.0 **硬跳到 1.06**——在一段本该连续
的运动中间出现不连续，表现就是"滑出到正常状态中间有个断层，还微微放大了一下"。

修法是让动画终点**等于元素即将保持的那个比例**：引入变量 `--dshrb-settle`
（静止 1 / 悬停 1.06），关键帧自第一帧之后的每一帧都写成它的倍数，最后一帧就是它本身。
这样"交还"变成无操作。`check.mjs` 有守卫断言末帧必须是 `scale(var(--dshrb-settle…))`，
且两个状态都真的声明了该变量（否则回退值会把尾部钉死在 1，断层原样回来）。

同一个隐患在按压回弹 `dshrb-jelly` / `dshrb-squash` 上同样存在（也是交还 `transform`），
所以那两组的首帧与末帧也一并改成 `--dshrb-settle` 的倍数。侧栏控件用同一组关键帧，
因此它也自己声明了 `--dshrb-settle:1`（它没有 hover 放大）。

回弹幅度与时长也放软了：`dshrb-reveal` 由 `.3s` 延到 `.44s`，落点偏差收到
约 6%→2.5%→2%→0.5%；`dshrb-jelly` 由 `.52s`/1.18 收到 `.46s`/1.12。

> 另有一处**覆盖**导致侧栏比悬浮更"硬"：侧栏曾残留一条自己的
> `animation:dshrb-reveal .26s cubic-bezier(.34,1.56,.64,1)`，写在样式表更后面，
> 于是覆盖了共享的时长与曲线——侧栏保留一个强过头弹簧而悬浮是缓出，且曲线自带的过头
> 与关键帧自带的回弹会叠加。现在 **`dshrb-reveal` 这一条**两条规则声明**完全相同的
> 时长与曲线**（都是 `.44s cubic-bezier(.22,1.1,.36,1)`），只有
> `transform-origin` 按界面不同。注意侧栏**必须自己声明一次**：它与悬浮是两个不同的类
> （`.dshrb-sb` / `.dshrb-btn`）、互不为祖先，没有可继承的规则。

> **但这条"完全一致"只覆盖 `dshrb-reveal`，不覆盖 `dshrb-jelly`。** 按下/回弹那对：
> `press` 两边相同（`.16s ease-out`），而 `release` 不同——侧栏 `.52s
> cubic-bezier(.36,1.4,.5,1)`，悬浮 `.46s cubic-bezier(.36,1.28,.5,1)`。
> 也就是说两条规则**共用同一份 `dshrb-jelly` 关键帧、但不共用时长与曲线**。
> 这个差异是否**有意**，从历史里没能确认；统一它会改变观感（小控件回弹快一点），
> 所以**保持原样并在此标注**，而不是靠猜"顺手对齐"。若确认应当一致，
> 要改的就是侧栏那一行。`check.mjs` 只断言 `dshrb-reveal` 两边一致——那是有意为之的
> 约束；对 `dshrb-jelly` 它不断言，因为真相是它们不一致。

### 点击后闪一下：展开动画被「交还」时又重播了

> 用户报告："两个按钮点击之后的果冻动画结束都会闪一下，就是消失又出现，很快的闪一下。"

`data-reveal='true'` 不只是"处于展开态"的标记，它就是展开动画的**触发器**。而它和按压/
回弹那对规则**在同一元素上抢同一个 `animation` 简写**：两者特异性相同（都是一个类 + 一个
属性选择器），胜负由源码顺序决定，而按压那对写在后面、点击期间一直赢。于是 `JELLY_MS`
（520ms）把 `data-anim` 清回 `""` 的瞬间，`animation` 简写被**交还**给展开规则——而"交还"
不是无操作：浏览器看到动画名变了，会把 `dshrb-reveal` 从头播一遍，0% 帧正是
`transform:scale(.5,1)` + `opacity:0`。控件先消失再长回来，每次点击一次，两个按钮都有。

实测（Chromium 154：把组件 emit 的属性按时序驱动，读 `getAnimations()` 与计算 opacity）：

| 时序 | 清除 `data-anim` 那一刻 | 该刻计算 opacity |
| --- | --- | --- |
| 旧：`data-reveal` 一直留在元素上 | `dshrb-reveal@0ms/running` | **0** |
| 新：按下即花掉这次展开 | `none` | 1 |
| 对照：未贴边的悬浮按钮（从不带 `data-reveal`） | `none` | 1 |

修法是把展开当成**一次性动画**（它本来就是这个语义），而不是"展开态的实时属性"：
`useRevealArm(revealed, interacting)` 在 `revealed` 的**上升沿**武装它，被这次展开期间的
第一次按压**永久解除**，于是那次交还落在静息规则上、什么也不改。离开该界面再进入会重新
武装（所以重新展开仍然有滑出动画）——这也是解除**不能**简单写成"`revealed` 为假"的
原因：那样属性会跨"收起/展开"一直留着，滑出动画从此再也不播。

"上一帧的 `revealed`"存的是 **state 而不是 ref**，因为 ref 在**被丢弃的那次渲染**里也会被
推进，而它支撑的那次 `setArmed` 会随渲染一起被丢掉——这个不对称可以吃掉一次武装，也可以
把武装重新加到**已经画好**的展开控件上（那就是原症状）。两处写入都用 React 文档里的
"渲染期调整 state"写法而不是 effect：effect 会在展开面**画出来之后**才加属性，控件会先以
完整尺寸显示一帧，再开始滑出。

按压动画正在跑时**不武装**是刻意留的一条分支：那时按压规则本来就压过展开规则，武装只会把
那次闪烁排到交还的那一刻。代价是明确的、**不是"几帧被盖住"**：落在果冻窗口里的那次进入会
**整段失去这次滑出动画**（下一次进入照常有）。反过来在果冻结束时补加属性，就是把属性加回
一个已经画好的元素上——那正是闪烁本身；两条路只能选一条，选便宜的那条。

配套的一处搬移：侧栏的 `transform-origin:left center` 从"展开触发器"规则搬到了
`.dshrb-sb` 基础规则。触发器现在会被按压花掉，留在那里的原点会随它一起消失，之后回弹就
从控件中心缩放，而控件是钉在左缘的。`check.mjs` 两半都断言（基础规则必须有该原点；触发器
上不许再有），因为"搬到基础规则"和"跟着旧规则被删掉"从外面看一模一样。

这套修法依赖两条**只能由静态断言看住**的关系，`check.mjs` 各有一条守卫：

1. **按压类必须比动画活得久**：`JELLY_MS`（JS 常量）不得小于 `[data-anim='release']` 上的
   CSS 时长，否则类会在果冻中途被摘掉、`transform` 从中间值跳回静息值。两者今天是相等的
   （定时器比动画早一个提交起算，所以类在果冻最后一帧左右才清，比较用 `>=`）。
2. **交还时刻不许有别的规则来抢 `animation`**：整套正确性建立在"`data-reveal` 与非空
   `data-anim` 永不同时在场"，而组件空闲时渲染的正是 `data-anim=''`——一条
   `[data-anim='']{animation:…}` 会恰好在交还那一刻起动动画。这条断言同时把"能动画这两个
   控件的规则"锁成已知的六条（reveal / press / release × 两个界面），因为行为断言只读组件
   发出的属性、看不见级联。

验证分三层，缺一层就会有看不见的洞：

| 层 | 在哪 | 能看见什么 |
| --- | --- | --- |
| 静态 | `check.mjs` | 样式表文本、关键帧、常量与规则之间的关系（上两条） |
| 行为 | `behaviour.mjs`（手写 hook 运行时，无 CSS 引擎） | 组件**发出**的属性在整个生命周期里的取值 |
| 级联 | `%TEMP%\dshrb-jelly-probe\`（真 Chromium + 真样式表） | `getAnimations()` 与计算 `opacity`——即"闪"本身 |

第三层是唯一能直接观察这个 bug 的地方，所以它被固化成一个可重跑的探针：
`run-probe.ps1` 把当前 `lib/client.js` 拷进探针目录（并打印它的 sha256），在 headless
Chromium 里同时重放**旧时序**（必须复现出 `dshrb-reveal@0ms/running` + `opacity:0`）和
**新时序**（必须 `none` + `opacity:1`），再跑一个"从不带 `data-reveal`"的对照，最后打印
四条 `VERDICT`。旧时序那一条是关键：它证明这个探针**能看见**自己的被测对象，而不是因为它
本来就不报警。

`neg.mjs` 有 7 条与本次相关的反向变异并全部被抓：两个界面各自退回"按状态取属性"、武装写成
非粘性、把**任意**边沿都当成武装（于是收起态也带着属性、下次进入再也不滑）、`JELLY_MS`
调短、给空闲按压类加动画规则、以及把侧栏原点从基础规则删掉。后三条专门用来证明上面那三条
静态守卫能看见它们自己的被测对象。

### 侧栏控件往旁边靠了 6px（而且必须靠在 wrapper 上）

侧栏控件用 `margin-left:-6px` 往侧栏边缘方向靠近一点。**这个偏移必须在
`.dshrb-sbwrap` 上，不能在收起态规则上**——原因就是下一节那个闪烁闭环。

`.dshrb-sbwrap` 在**所有状态**下都是同一个盒子，所以它的左边缘在"收起/展开"两种状态
之间**不变**，几何上无法把指针甩出去。如果这条 `margin-left` 写在
`.dshrb-sb[data-rail='true']` 上，它就只在收起态存在：指针一进去 → 状态切换 → 偏移
消失 → 盒子横跳 6px 脱离指针 → `pointerleave` → 收回 → 偏移回来又落回指针下 →
无限循环。

这也**没有改动 DSH 侧栏或头像行的任何宽度**：它是本插件自己盒子上的外边距，只影响
自己占据的空间，不动宿主的列宽。`check.mjs` 有两条守卫：偏移必须在 wrapper 上，且
**任何以 `data-rail` 为条件的规则都不得声明** `margin`/`left`/`right`/`translate`/
`position`。

### 侧栏控件展开后只有图标，没有文字

侧栏控件展开（`data-wide='true'`）时**只有电源图标**。它以前会在图标右边印"电源" /
`Power` 两个字，结果是它比旁边的图标按钮宽不少、还会顶动头像行。现在文字标签**元素和
样式规则都已删除**。

#### 展开后不再是"那么窄"

删掉文字时留下了一句 `[data-wide='true']{width:auto}`，而 `width:auto` 比听起来窄得多：
没有内边距、只有一个 16px 图标，按钮于是收缩到 **16px 宽**——比它刚从中长出来的 14px
细条几乎没宽多少。用户的原话是"侧栏按钮打开后太窄了，不用收的那么窄的"。

现在这句覆盖**整条删掉**：展开态就是基准规则的 **32×32 方形**，与旁边的图标按钮同重。
没有任何规则按"落座状态"给这个按钮定尺寸。`check.mjs` 的守卫随之反转：原来是"宽态不留
内边距"，现在是"任何以落座状态为条件的规则都不得声明 `width`"+"基准规则必须是 32×32 且
无内边距"。

这里曾经还有一个 `data-wide` 属性，镜像宿主的 `wide` prop。它**已经是死代码**：账户行定位
的门禁其实是 **wrapper 上的 `data-dshrb-inrow`**（另一个元素上的另一个属性），而 `data-wide`
没有任何规则读它，包外也没有消费者（宿主 bundle 自己的 `[data-wide=wide]` 选择器都限定在
它们自己的 `_trigger` 类下、且用的是 `"wide"/"rail"` 值，与这里的 `"true"/"false"` 不可能
相撞）。死标记会让人误以为改它会有作用，所以**属性已删除**，`check.mjs` 改为断言
wrapper 上的 `data-dshrb-inrow` 是唯一的落座标记。

#### wrapper 的命中盒必须"贴合"，否则空行也变成悬停区

把指针事件移到 wrapper 上之后，**wrapper 的盒子就是控件的命中区**——而它是 `flex:none` 的
auto 宽度项，一旦容器沿某个轴 `stretch`，它就会被**撑到容器宽度**。

实测（同一对盒子，五种宿主布局；`slack` = wrapper 比细条多出来的可点区域）：

| 布局 | wrapper | 细条 | 多余命中区 |
| --- | --- | --- | --- |
| 宽态账户行（`align-items:center`） | 14×32 | 14×32 | 0 ✅ |
| 同一行改成 `stretch` | 14×32 | 14×32 | 0 ✅ |
| 收起图标栏（居中列） | 14×32 | 14×32 | 0 ✅ |
| 收起图标栏（默认 `stretch`） | **36×32** | 14×32 | **22px** |
| 无 web-all，宿主自己的堆叠脚部 | **734×32** | 14×32 | **720px（整行）** |

> 上表是**当年**（wrapper 还没有 `fit-content` 时）的五种布局实测记录，保留原样不改。
> 注意最后一行描述的那个布局——"没有 web-all 时宿主自己的堆叠脚部"——**现在不再是
> 无 web-all 环境的默认形态**：本轮加的兜底重排会把那个 foot 变成 wrap 行（与装了
> web-all 时同样的形态），实测 wrapper 与控件同盒（`32×32`，`wrapper-minus-button=0x0`，
> 两个分支的数值一致）。保留这一行是因为它是"wrapper 为什么会膨胀"这条推理的原始证据；
> 它描述的布局在控件被设置关掉时仍然存在，只是那时没有 wrapper 可量。

后两种会把细条**右边一大片空行**变成悬停区：鼠标离控件远远的就会把它展开。修法是
`width:fit-content;height:fit-content`，把五种布局全部收成"恰好等于细条"。

> 上表最后一行那个 **734px 是探针容器宽度的函数**，不是一条通用常量：另一位 reviewer 用更窄的
> 探针容器独立复现到同一现象，量到的是 **306px**。同一个膨胀、两个数字，取决于测量时的容器
> 宽度——所以这里给的结论是"膨胀到容器宽、可到整行"，具体像素数不必当常数引用。关键拓扑：
> 插槽容器是 `display:contents`，所以 wrapper 是脚部那个 column 的**直接**子元素；该 column 的
> `align-items` 默认 `stretch`，这就是膨胀的来源，也正是 `fit-content` 能修掉它的原因。

这是**上一轮把事件移上 wrapper 时引入的副作用**，靠读代码看不出来（取决于宿主的 flex
对齐，而那几个容器不是本插件的），必须实测。`check.mjs` 有一条守卫断言 wrapper 声明了
`fit-content`。

### 展开动画的「包含不变量」（上下边缘闪烁的根因）

**这是这个动画唯一不许破的规则：动画的每一帧，渲染出来的盒子都必须包含指针进来的那条
收起细条。** 指针是落在细条上的，只要有一帧盖不住它，就会触发 `pointerleave` → 收回 →
细条又回到指针下 → 再次展开，只要光标不动就无限循环。

用户报的就是这个，而且描述得相当准确：

> 侧边按钮是不是收起状态比展开状态要高一些，鼠标在收起细条的上下边位置的时候打开后会
> 立刻关闭，随后又立刻打开，造成闪烁情况

两个状态**其实是同高的**（32px）。破约的是关键帧的第一帧 `0%{transform:scale(.5,.72)}`：
纵向压到 72%，32px 高的控件在前几帧只有 **23px** 高，上下各少掉 4.5px，指针就不在元素
上了。悬浮条同样中招——它 44px 高，每端少掉 6.2px。

实测（无头 Chrome，在细条上/下边缘取点问 `document.elementFromPoint`，把动画冻结在指定帧）：

| 帧 | 修复前渲染尺寸 | 顶边命中 | 底边命中 |
| --- | --- | --- | --- |
| 0% | 16.0 × **23.0** | wrapper | wrapper |
| 26% | 33.9 × **30.4** | BUTTON | wrapper |
| 48% 起 | ~32 × ~32 | BUTTON | BUTTON |

修复后每一帧两个边缘都命中 BUTTON。所以纵向因子**永远不低于 1**
（`1, 1.04, 1.01, 1.005, 1.002, 1`）：控件只允许从静息高度往上长，jelly 的观感变成
"横向滑出 + 一次呼吸"，而不是纵向压扁。横向因子可以缩小，因为它锚定在贴边的那一侧，
而细条比按钮窄得多——0.5 × 44px 仍有 22px，对着 8px 的细条是安全的。

#### 侧栏为什么还要把指针事件挪到 wrapper 上

横向还有第二个隐患：展开时布局宽度 14→32px 是带 `0.18s` 过渡的，而动画第一帧又乘 0.5，
所以最初几帧的可见宽度只有 **7px**（小于细条的 14px），同样会把指针甩出去。

所以侧栏的 `onPointerEnter`/`onPointerLeave` **从按钮移到了 `.dshrb-sbwrap`**：

- wrapper **不带任何 transform**，它的盒子就是布局盒——两种状态下都是 32px 高，宽度只会
  从细条的 14px 单调变到按钮的 32px，因此**永远包含细条**，也包含整个动画；
- 按钮仍是它的后代，所以指针在两者之间移动不算跨越边界，不会触发任何事件；
- 焦点处理仍留在按钮上：键盘展开没有指针，也就没有这个隐患。

这样侧栏的闪烁在结构上**不可能**再发生，与动画参数无关。`check.mjs` 三条守卫：纵向因子
全部 ≥ 1、第一帧的横向因子 × `SIZE` ≥ 细条宽、以及"侧栏的指针展开必须来自不带 transform
的 wrapper，按钮自己不得再带 `onPointerEnter`"。

> 守卫自身也踩过一次坑：最初的因子提取用了非贪婪正则，被 `calc(var(--dshrb-settle,1) * 1.04)`
> 里那个内层 `)` 提前截断，把每个因子都读成回退值 `1`——**无论关键帧写什么都会通过**。
> 现在改成括号配平扫描，并额外断言"确实解析到 6 组"，因为**看不清的守卫不是守卫**。

### 点击菜单后必须重新贴边（不是常驻展开）

用户第二次描述这个问题时给出了完整路径：

> 鼠标移上去，按钮展开，鼠标点击一次，菜单打开，鼠标点击旁边空白位置，菜单收回，
> （按钮并没有收回侧边）… 按钮在随后就没收回侧边，常驻展开了，必须要在拖动一次重新靠边
> 才可以正常收回

根因**不在指针状态，而在点击本身改写了位置**。原来的"点击"分支在收起态被点击时会把位置重写成
`{side: null, collapsed: false}` 并**持久化**：

```js
// 旧代码：点了就不再贴边
setPos(function (previous) {
  if (!previous.collapsed) return previous
  var next = { x: previous.x, y: previous.y, side: null, collapsed: false }
  storePos(next)
  return next
})
```

菜单打开期间的展开**本来就由 `menu.phase !== null` 保证**，所以这次重写纯属多余——但它的
后果活得比菜单久：菜单关掉时控件已经不是"贴边收起态"，只能靠再拖一次重新 `settle()` 才收回。

修法是**点击只开菜单，什么都不改**：

```js
if (!drag.moved) {
  menu.open()
  return
}
```

这也是更诚实的行为：没有任何东西移动过控件，就不该移动它；**只有拖拽才改写它的位置**。

配套还要删掉 `onPointerLeave` 里那句 `if (menu.phase === null)` 守卫——它会吞掉菜单打开期间
的 leave，把 `hovered` 卡在 `true`，于是菜单关闭后控件同样常驻展开。两处**必须一起改**，只改
一处会以另一种形态复现同一个症状（悬浮按钮和侧栏都有这句守卫，都已删除）。

`behaviour.mjs` 用一条完整路径守着它：贴边 → 悬停 → 点击开菜单（此时断言**持久化的位置仍是
贴边收起**）→ 点击空白关闭 → 断言控件回到收起细条。

### 拖动时保持展开形态（"先收回再突然出现"的修复）

用户报告：鼠标放到细条上展开后，**按住往外拖**，控件会先收回细条，等鼠标移动后才突然
出现在光标下。根因在 `onPointerDown` 里的一行 `setHovered(false)`：按下瞬间 `hovered`
被清掉，而展开条件当时只看 `hovered`，于是控件立刻塌回收起态；直到第一次
`pointermove`（它会直接清掉 `collapsed`）才恢复成完整按钮。

修法是让**拖拽过程本身**也算作展开理由：

```js
var revealed = strip && (hovered || dragging || menu.phase !== null)
```

这样按下即展开、整个手势期间保持展开，控件从一开始就是以展开形态跟着鼠标走。
`behaviour.mjs` 的断言在**移动之前**就检查（按下后立刻必须是展开态），这样守的是"按下
这个动作本身"而不是"移动的副产物"。

### 菜单字体跟随主题

菜单的字体用宿主自己声明的令牌 `--dsw-font-family`（`-apple-system, BlinkMacSystemFont,
Segoe UI, PingFang SC, …`），而不是靠继承"碰巧"拿到根元素的字体族。字号与行高仍显式
写明（13px / 1.5）：面板不是正文块，不该跟着用户的"内容字号"设置一起缩放。

### 侧栏细条为什么不贴侧栏边缘

早先细条是用负边距（抵消侧栏自己的内边距令牌 `--dsh-sidebar-inline-padding`，实测
`12px`）拉到侧栏左边缘的，而那条负边距**只写在"收起"状态上**。于是鼠标一进细条 →
状态切换 → 负边距消失 → 盒子横跳一个内边距宽度、脱离指针 → `pointerleave` → 收回 →
负边距回来又落到指针下 → 无限循环。表现就是**按钮弹出后立刻缩回、不停闪烁**，根本
悬停不住。

现在负边距整个删掉了：控件在头像行里向右生长，左边缘**永远不动**，展开只从右边的
头像行借宽度，所以指针进入的那一像素在整段展开过程中始终被覆盖，几何上不可能再伪造
出指针事件。`check.mjs` 里有一条守卫断言"任何以 `data-rail='true'` 为条件的规则都不
得声明 `margin`"，把这套机制钉死。

### 侧栏电源怎么坐进头像行

`sidebar.footer.action` 座位自己的容器是 `display:contents`，所以控件实际是侧栏
`footArea` 的直接子元素。而外壳的 `footArea` 本身是**竖直排列**（footerActions 一
行、账号行一行），按外壳自己的规则这个控件会独占一行、落在头像**上方**——这就是用户
说的"缩在红框位置"。它必须落进头像左侧，而且**装不装 web-all 都要在那个位置**。

`@linxin666/dsh-remote-web-ui`（web-all 的依赖）会把这个 foot 重排成一行 wrap flex，
本插件正是加入那一行：`order:2` 排在账号行的 `order:3` 之前 → 落在头像左边；它给自己
的电话入口 `order:4`，排到更右边。

**一条路，只由本插件自己的状态武装**：

| 状态 | 谁负责重排 |
| --- | --- |
| 装了 web-all | web-all 重排；本插件声明自己的 `flex`/`order` 去**加入**那一行，并复刻同一段重排（数值相同，两张表同时生效等于空操作） |
| 没装 web-all | 本插件的这段重排就是唯一来源 |

**复刻的六条声明**（数值照抄 web-all，不是"类似值"，这样两种环境的落位才一致；第 4–6 条是
为"不改变别的插件看到的布局"而照抄的）：

```css
/* 1 脚部变成可换行的行 */
[class*=footArea]:has(.dshrb-sbwrap[data-dshrb-inrow]){
  flex-direction:row;flex-wrap:wrap;align-items:center}
/* 2 化掉整宽的 footer 盒子，让座位里的控件成为脚部的直接 flex 项 */
[class*=footArea]:has(.dshrb-sbwrap[data-dshrb-inrow])
  > [class*=footerActions]{display:contents}
/* 3 放开账号盒子的整行宽度（`width:auto` 是实测踩出来的，见下） */
[class*=footArea]:has(.dshrb-sbwrap[data-dshrb-inrow])
  > [class*=settingsArea]{order:3;flex:1 1 auto;width:auto;min-width:0}
/* 4 脚部其余直接子项（别的插件的面板、用量卡）仍各自独占一整行 */
[class*=footArea]:has(.dshrb-sbwrap[data-dshrb-inrow])
  > :not([class*=settingsArea]):not([class*=footerActions]){
  flex:1 1 100%;min-width:0}
/* 5 座位里除本插件外的一切注册项，同样保留独占一行 */
[class*=footArea]:has(.dshrb-sbwrap[data-dshrb-inrow])
  > [class*=footerActions] > [data-slot='sidebar.footer.action']
  > :not([data-dsh-part='entry']):not([class*=entryRow]):not([class*=dshrb-]){
  flex:1 1 100%;min-width:0}
/* 6 座位里"别人家的条目"按 web-all 的数值安排（第 5 条豁免了它们，就得给它们去处） */
[class*=footArea]:has(.dshrb-sbwrap[data-dshrb-inrow])
  > [class*=footerActions] > [data-slot='sidebar.footer.action']
  > [data-dsh-part='entry'],
[class*=footArea]:has(.dshrb-sbwrap[data-dshrb-inrow])
  > [class*=footerActions] > [data-slot='sidebar.footer.action']
  > [class*=entryRow]{
  flex:0 0 auto;order:4;min-width:0}
```

`width:auto` 那一条是**实测踩出来的**，不是顺手补的：外壳给 `settingsArea` 声明了
`width:100%`，所以 flex-basis 就是整行，账号行必然换行到第二行，控件又回到头像上方。
第一版就漏了它，无头 Chromium 里 `sameRow=false` 直接暴露。

**早先这里是"装了/没装"两条互斥分支，而那个设计是错的**——下一节就是它翻车的过程。

**`:has()` 是硬依赖**：不支持的浏览器会因选择器无效而整条丢弃，控件退回外壳的堆叠
布局——与完全没有兜底等价，不会更糟。应用自带 Chromium 152，支持。

**三个边界都是刻意的**：

- 所有改**共享盒子**（`footArea` 及其子盒子）的规则都带
  `:has(.dshrb-sbwrap[data-dshrb-inrow])`，即只在"确实存在本插件的宽侧栏控件"的那个
  foot 上生效。用户把侧栏开关关掉时，foot 仍是外壳的**竖列**，此时 `flex:1 1 100%`
  的 `100%` 会按**高度**解析，把别的插件的控件拉成满高——这条作用域就是拦这个的。
- 座位是共享的，所以另加一条给 `:not([class*=dshrb-])`（即除本插件外的一切注册项）
  保留 `flex:1 1 100%` 独占一行，与 web-all 装着的表现一致，不把别人的块挤进底行。
  这一条还带着 web-all 自己的两项豁免（`[data-dsh-part='entry']` / `[class*=entryRow]`）：
  本插件的选择器权重更高，不照抄就会把 web-all 的豁免压掉、把别人的条目也变成独占一行；
  豁免出来的条目由紧接的一条按 web-all 的数值（`flex:0 0 auto;order:4`）安排。
- 脚部**其余**直接子项（第 4 条声明）同样照抄：那些是别的插件自己的面板、用量卡，脚部从
  竖列变成行之后它们会从"独占一行"滑进底行去挤账号行，`flex:1 1 100%` 把它们放回原来的
  堆叠。它们的 `order` 是默认的 `0`，排在本插件的 `order:2` 与账号行的 `order:3` 之前，
  所以仍在第一行——与 shell 竖列时的相对顺序一致，因此这一条不需要写 `order`。

`!important` 只出现在**占位规则**（把控件放进那一行）上，理由是**确定性**而非随手：
web-all 给它不认识的每个 action 都下 `flex:100%;order:1`（正是"独占一行"那条），那条
选择器按级联对 `:not` 的算法算权重是 (0,6,0)，与占位选择器**同权重**——同权重由"哪张
样式表先被求值"决定胜负，装插件顺序能改变布局就是等着被报的 bug。重排那几条不写
`!important`：那里没有需要压制的对手，web-all 声明的是同样的值，谁赢都一样。

规则由本组件自己的 `data-dshrb-inrow` 门控，值来自外壳传进来的 `wide` prop。折叠成
图标 rail 时没有头像行（那是个居中 36px 竖列），`order` 会打乱 rail 的堆叠，所以那里
不启用。

> 真实环境（把 web-all 关掉）由用户实测，结论与复现页面不同——原因在下一节。复现页面
> 用的是"外壳真实规则 + 本插件真实样式表"，但它按"有/无标记"构造页面，因此漏掉了
> "标记残留"这一态。这条教训比那次的坐标数字更值得留在文件里。

#### 「关掉 web-all 后按钮不在头像行」：门是用"标记不存在"写的

用户原话：*关掉 web-all 这个插件后，侧栏按钮并没有和头像栏在同一行*。

原因是早先那个**两分支构造**：分支 B 的条件是 `html:not(:has([data-dsh-frame]))`，即
"web-all 的标记不存在"。但**标记不存在 ≠ 重排不存在**——这里有**三个状态，不是两个**：

| 状态 | `data-dsh-frame` | web-all 的重排 | 旧写法命中 |
| --- | --- | --- | --- |
| 装着 web-all | 有 | 有 | 分支 A |
| 从没装过 / 干净加载 | 无 | 无 | 分支 B ✓ |
| **装过又关掉** | **有（残留）** | **无** | 分支 A —— 只声明 `order:2`，背后没有重排 |

第三态就是失败态。标记是**单向门闩**：`@linxin666/*` 里
`removeAttribute("data-dsh-frame")` **一处都没有**（全量检索），所以那个包一旦跑过，标记
就留在外壳 frame 上；它的样式表随插件被卸下之后，标记照样在。此时分支 B 永远不成立，而
分支 A 照旧生效：脚部还是外壳的**列**，`order:2` 没有行可以排序，控件于是独占一行、
落在头像上方。

**修法**：删掉"按标记有无"的分支，重排变成**一条路**，唯一的门是本插件自己的
`data-dshrb-inrow`（值来自它自己的 `wide`）。web-all 也在时，因为复刻的数值与它相同，
两张表同时生效是空操作；选择器同权重时"谁先被求值"不再影响结果，因为值一样。

**顺带修掉的一处**：那段重排原本只压制"非本插件"的注册项（`flex:1 1 100%`），而 web-all
会豁免它自己家族的条目（`[data-dsh-part='entry']` / `[class*=entryRow]`）。本插件选择器
权重更高，所以 web-all 装着时它会把那条豁免**压掉**，把别人的条目也变成独占一行——现在
照抄了同样的 `:not()`，并补上 web-all 对它们的那条规则（`flex:0 0 auto;order:4`）。

**验证**：

- `check.mjs` 新增 `no layout rule keys on another bundle's marker`——整张表里任何规则的选择器
  都不许出现 `data-dsh-frame`；另加"重排与 web-all 数值逐条一致"的比对。旧的两条守卫
  （"两分支互斥"、"要求 `:not([data-sidebar-collapsed])`"）随之删除，因为它们断言的是坏设计。
- 守卫的集合键从"带 `:has()`"改成"碰到共享盒子的规则"：否则一个把 `:has()` 作用域删掉的
  反向注入会**掉出守卫集合**从而被漏掉——守卫自己也得有能失败的余地。
- 反向注入：`reflowgate`（把标记门加回去）必须被抓住；`footscope`、`footwidth` 的锚点随
  选择器改写同步更新（锚点是字面量，所以改了拼写就要改锚点，这是这套方法的已知边界）。
- **真实环境**：为了拿到"第三态"的现场，插件里临时加过一段只读诊断（把 frame 上有没有标记、
  wrapper 上有没有 `data-dshrb-inrow`、脚部是不是 row、控件盒与账号盒是否同行、哪几条规则真的
  匹配到控件，写进 `localStorage['dshrb-diag']`）。用户重启后确认**没有 web-all 时按钮已经正常
  落在头像行**；诊断随即从包里删除，不随发布版发布（那个 `dshrb-diag` 键会留在浏览器存储里，
  无害，可直接忽略）。

**为什么不能"有 web-all 就删掉这段"**（本轮实测 web-all 的真规则）：web-all 对**没贴它私有**
`data-dsh-part=entry` 标记的外来控件给的是 `flex:100%;order:1`——独占整行，而且排在头像行
**前面**。所以"删掉我们的、交给 web-all 摆"不是交给它管，而是没人管。要让它摆，就得贴上它私有的
entry 标记，那只在它启用时成立；它一关又得回到自己这套 ⇒ 两套并存 + 重新去猜状态。

而"住进头像那一格"这条更优雅的路被官方堵死了：`sidebar.settings` 与 `triggerRow` 内部的
`settings.launcher` 都是 `kind: "single"`（注册进去是与官方账号行**抢同一个位置**，可能把头像
顶掉），插槽宿主的容器本身是 `display:contents`（不带来一行），非折叠态 `settingsArea` 还是
`block`——头像行内部没有留给第三方的落座位。因此这段重排是落座的**唯一手段**，它的适配边界是
"任何只改这一格布局/样式的插件"（值取标准行布局值 + 只由本插件自己的状态武装）；把头像搬出
`footArea` 的插件，CSS 无法跟随，只剩"测量矩形 + 绝对定位跟随"这一条路（未实现）。

> 诚实交代："两分支盒子坐标完全一致（控件 `6,6,32,32`、账号 `38,12,210,20`、`sameRow=true`）"
> 这句曾写在本节和两份 README 里，它是**复现页面**的结论，只覆盖前两个状态。用户在真实
> 环境（第三态）看到的相反结果才是对的，那句话已删除。

### 二次确认只在真有任务在跑时才问

点「重启」/「退出」后是否弹确认，取决于宿主回答的 `working`：

```js
// 宿主半：进程内所有 agent 的权威状态位，子代理天然包含在内
ctx.agents.list().some((agent) => agent.status === "running")
```

- **有任务在跑**（含子代理）→ 弹二次确认，文案提示会被中断。
- **没有任何任务** → 直接执行。空闲时多问一次只是摩擦。
- **问不出来**（`agents` 服务缺失、读取抛错、字段缺失）→ **按"有任务"处理**，
  仍然弹确认。重启会毁掉看不见的工作，误问一次远比误杀一次轻。

`ctx.agents` 是**进程级**注册表，子代理通过 `parent.ctx.agents.create({ parentAgent })`
落进同一张表，所以 `list()` 一次就覆盖子代理，不必递归。（边界：跨进程子代理不在
这张表里；本版本组合未随附该类 provider。）

探测时机是**菜单打开时**，不是点击时：点击路径保持同步，不会因为一次往返而卡顿；
菜单打开到点击之间人手的间隔远大于本机往返，所以答案几乎总是已就绪。

**确认之后（`phase = "busy"`）面板必须消失，两个界面都一样。** 面板的 else 分支
渲染的是带**可点击确认按钮**的二次确认：如果 busy 阶段它还在，再按一次确认就会第二次
发出 `api.action`，宿主只会回 `already-running`，随后在忙碌提示之上再叠一层错误面板。
悬浮那份从一开始就把 `busy` 排除在外，侧栏那份没有，于是同一个状态在两个界面上表现不同
——`busy` 时只留忙碌提示，`aria-expanded` 也跟着报 false（面板确实不在，报 true 是
对辅助技术的谎报）。`behaviour.mjs` 对两个界面各有断言，并做过反向注入。
（这条是只读 review 找出来的，不是自己发现的。）

**悬浮按钮的点击必须能关掉自己的菜单。** 按下时无条件关面板（拖动不该把菜单留在原地），
抬起时若是"没移动的点击"就再开——两条相互抵消，于是那个按钮永远关不掉自己的菜单，还会
重放一次 `dshrb-pop` 闪烁；而侧栏那份本来就是 toggle，两个界面行为不一致。
现在手势记录按下时面板是否已开（`drag.wasOpen`），抬起时只在原本是关的情况下才开。

**设置写失败要把值恢复回去。** 失败路径原本保留乐观值、文案却说"设置未改变"，而且那个
未落盘的值已经通过 `BroadcastChannel` 广播给其他窗口，而其他窗口的 `onMessage` 会无条件
采纳。现在失败时 `adopt(previous, true)` 把值放回**写入前**的状态（这才让那句文案成立，
也让开关回到持久化的真实位置），并且只广播已确认落盘的值。

两个开关都在插件自己的配置页（槽位 `plugins.bundle.config`，key = 包名）。**开关状态
改完立即生效，不需要刷新页面**——`configStore.save()` 会先乐观更新内存值并同步通知
订阅者，所以当前页面立刻重绘；`BroadcastChannel` 只负责把变化**同步到另一个窗口**
（多个 DSH 窗口之间）。该通道的生命周期挂在 bundle 实例上（`apply` 里 `attach()`，
卸载时 `detach()`），因为客户端热重载会重新求值整个工厂函数。

> 为什么开关不放在插件管理器的卡片上？因为插件管理器按**bundle 行**启停，粒度是
> 「装不装这个插件」，而不是「画哪一个界面」。安装两个包会得到两张卡片和两份代码
> 副本，所以两个界面共用一份实现，各自的开关归插件自己管。

## 安全护栏

### 为什么必须自己调用 `requestRejection`

宿主的鉴权挂在 `kind: "prefix"`、`path: "/api"` 上，而 webserver 的派发顺序是
**先查 exact 表、未命中才看 prefix 表**。本插件注册的三条路由都是 exact，正好命中在
`/api` 前缀门**之前**——也就是说，它们会**遮蔽**宿主对所有 `/api` 接口的鉴权。

实测（无 cookie，对着真实运行的宿主）：

| 请求 | 结果 |
| --- | --- |
| `/api/dsh-restart/status` | **200** ← 被遮蔽，没走鉴权 |
| `/api/session/list` | 401 |
| `/api/connection/status` | 401 |

浏览器方向的 CSRF 被本插件自己的 `origin` / `sec-fetch-site` 判断挡着，但**本机任意进程**
都能直接 POST `restart`/`quit`，而它对别的 `/api` 接口没有这个能力——这就是权限模型被削弱。

所以三个 handler 现在都先调用宿主自己的 `connection.requestRejection(req)`（返回 401 / 403，
或 `undefined` 表示放行），保留 loopback 判断作为额外一层。复用宿主自己的权威实现，才能
保证插件和宿主处在**同一套**权限模型里，而不是旁边。

| 场景 | 行为 |
| --- | --- |
| **未通过宿主鉴权** | 三个路由都先调用宿主的 `connection.requestRejection()`，未鉴权 → 401，围栏不过 → 403 |
| pid 复用：`MainPid` 已被别的进程占用 | 比对 `ExecutablePath`，不一致就**拒绝**并退 **3**，绝不误杀 |
| `MainPid` 的映像路径**读不出来** | 视为"无法确认"，同样**拒绝**（退 **3**）——否则这道唯一的检查会在最需要它的时刻静默失效 |
| pid 复用：`HostPid` 已被别的进程占用 | 杀之前同样比对映像路径；不一致则跳过并记日志 |
| **重启目标不存在**（应用被就地更新 / 路径被移除） | 在**杀任何东西之前**就 `Test-Path` 校验并以退出码 3 拒绝——绝不做"关掉了却打不开"的事 |
| 主进程已经消失 | 直接退出 0，什么都不做 |
| 主进程 `taskkill` 后仍不退出 | 最多等 `waitForExitSeconds`，超时则**放弃重启**（不会拉起第二个实例） |
| 三条件超时未满足 | 记 `WARNING` 并写明哪个条件未满足，继续尝试拉起 |
| WMI 不可用或被拒绝 | 引导进程以退出码 3 拒绝，宿主半回 500，界面显示失败 |
| 非 Windows / 非桌面版 | 宿主半回答 `supported: false`，**界面不渲染按钮** |
| 非 loopback 请求 | 403 |
| action 非法或空 | 400，且在启动任何进程之前就拦下 |
| 请求体异常或超 4KB | 400 |
| 重复请求（多窗口 / 双击）：已有操作在进行 | 409 `already-running`，界面提示"已在其他窗口发起" |
| 引导进程挂死 | `BOOTSTRAP_TIMEOUT_MS`（30s）后判定失败并释放闸门，避免界面永久点不动 |
| 配置项类型不对 | 回落到默认值，绝不因此让插件加载失败 |

### 退出码 3 与拒绝标记：区分"没动手就拒绝"与"动手中途失败"

一次性闸门（同一时刻只允许一个动作）**只在安全时才释放**。helper 用**退出码 3** 表示
「在碰任何东西之前就拒绝了」——WMI 不可用、pid 校验不过（含映像路径读不出来）、
重启目标不存在。这些情况下什么都没被杀，重试是安全的，所以宿主半释放闸门。

其他非零退出码一律**保持闸门占用**：那意味着 helper 可能已经杀了进程树，此时放行第二次
尝试会让两个重启互相竞争。退出码 1 专门留给这一类——`taskkill` 后壳仍不退出、以及拉起
新实例失败，两者都发生在**动手之后**。所以"拒绝"和"失败"在退出码上是分开的：
**3 = 没动手，1 = 动了但没成**。

**但退出码只覆盖引导阶段。** 真正检查 shell 身份的那些守卫跑在**工作阶段**，而引导阶段
早就以退出码 0 退出了——宿主看不到它们。这条路径如果不管，用户在 pid 复用被拒绝后会
**永久点不动按钮**（每次都是 409 `already-running`），只能手动重启应用才能恢复。

所以工作阶段的拒绝会额外写一个**标记文件** `restart-button.refused`：

- 每次启动前先删掉它，所以读到的只可能来自本次；
- 下一次点击时再读（那时工作进程早已结束，答案是稳定的）——读到就释放闸门，
  并回 500 `refused` **带出原因**；界面的失败文案就是"`refused` + 原因"，
  因为 `refused` 只说明类别，原因才说明是哪个成员（pid 复用会同时列出两个可执行文件路径）。
- `status` 也会带 `refused` 字段，但**客户端故意不读它**，它是**诊断**用而非 UI 通道：
  用户该看到原因的地方是重试那次（500 + `reason`），而不是打开菜单时。
  留着它的价值是让"闸门卡住"这件事在**点击之前**对运维/未来 UI 可见——
  "按钮没反应"和"按钮被挡住了，原因是这个"是两回事。
  （这里曾经写着"界面据此说明为什么被挡"，那是一句空头承诺：客户端从未读这个字段。）

**为什么不在启动时就等？** 因为引导握手的前提就是 HTTP 响应**立刻**返回——页面必须
活到收到响应，之后壳才会被杀。为了读一个标记而把响应推迟到工作阶段结束，会破坏这个前提。

> 早期版本对**所有**失败都释放闸门，那会让"杀完才发现拉不起来"的失败被连点成多个并发
> 重启；而只认退出码的版本又覆盖不到工作阶段。现在的区分同时避开两者。

### 1. 宿主半的可选 `config` 块

挂在 bundle 的 `insert` 行上（同 DSH 其他插件）：

```yaml
- insert:
    - id: ui-restart-button
      name: dsh-power-button
      config:
        settleMs: 500            # worker 启动到杀掉主进程之间的最短间隔
        waitForExitSeconds: 20   # 等"三条件"成立的上限；超时则记录后继续
```

这两项是与机器性能相关的时序，默认值在本机实测够用；慢机可调大。

### 交接给窗口系统的细节

三条容易踩的坑，都已在 CSS 里处理：

- **控件上必须 `-webkit-app-region: no-drag`。** 否则鼠标事件根本到不了页面：
  DSH 的标题栏规则把窗口顶部划成原生拖动区（`[data-windows-titlebar] .BynINW_frame:before`
  设 `-webkit-app-region:drag`），OS 在页面拿到指针事件**之前**就把它解析掉了，
  于是拖按钮变成拖窗口、菜单也收不到 `pointermove`。
- **但 `no-drag` 绝不能声明在铺满视口的元素上**——这条是踩过的坑。
  `.dshrb-root` 是 `inset:0` 的覆盖层，曾经在它上面写了 `no-drag`，结果
  **整个窗口都拖不动了**。原因是这个声明的语义是「从拖动区里挖掉自己这块」，
  是几何计算：覆盖层盖住了标题栏那一条，就等于把它从拖动区里挖掉，与 `z-index`
  无关，`pointer-events:none` 也拦不住（DSH 自己的 `Vb49yG_dragBand` 就是
  `pointer-events:none` 的整窗拖拽带，并且靠**加** `no-drag` 来关掉它）。
  规则：**覆盖视口的元素一条 app-region 都不带。** `check.mjs` 里有一条断言专门守这条。
- **根的 `z-index` 用了 2147483600。** DSH 自身的层级上限是 1100，贴近窗口顶部时
  悬浮按钮会被其他层盖住。
- **两处菜单的 DOM 挂载点必须一致，否则同一份组件会渲染成两个样子。** 两个菜单共用
  一个组件、一个 class，所以"侧栏那份看起来不一样"只可能来自**挂载环境**：悬浮面板
  由 `FloatingPower` 渲染在自己的 body 级 overlay 里，而侧栏面板原本渲染在**侧栏列内部**
  （那正是它的 slot 所在）。侧栏列是 `overflow:hidden`，并且 web-all 在
  `@media (max-width:768px)` 下给它 `transform:translateX(0)`——`transform` 会让该列成为
  `position:fixed` 后代的**包含块**，于是渲染在列里的固定面板被裁到列边界（实测：有该规则时
  面板自身像素在列边缘止住、露出页面；没有时不会，且列的 `offsetParent` 关系随之变化）。
  现在侧栏面板、忙碌提示与水珠都通过 `createPortal` 挂到同一个宿主，与悬浮那份同祖先、
  同层叠上下文、同包含块。

  **宿主放在插件自己的 `div[data-dsh-restart-root]` 容器内，不是 `body` 的直接子元素。**
  理由是两条：其一，铺满视口的元素会参与窗口 app-region 计算（官方基础样式表把 `body`
  直接子元素变成 `no-drag` 区；该规则带 `html[data-platform=darwin]` 前缀、是 macOS 专属，
  Windows 不适用，但插件不该依赖这个作用域一直成立）；其二，宿主由本实例创建、随容器一起
  被既有的陈旧容器清扫带走，因此不需要第二个清扫步骤、也不会出现"热重载时误认并删除新实例
  宿主"的问题。

  React 挂载点因此改成容器内的**另一个**带 `data-dshrb-mount` 标记的 div（与宿主是兄弟）：
  把已有子节点的容器交给 React，它会在 mount 时清空那些子节点，也就把宿主删掉。
  实测新旧结构的 `elementFromPoint` 完全一致（两处 overlay 都可达），层级没有变化。

### 面板与控件是硬不透明的，不跟随宿主菜单的透明度

DSH 自己的弹层底用的是 `--dsw-specific-menu`，它经 `--dsw-menu-surface-fill` 解析为
`#f8f9fa94`（浅色）/ `#43454a73`（深色）——**尾部十六进制对是 alpha**，也就是约
58% / 45% 不透明。DSH 自己会**配套**使用 `backdrop-filter:var(--dsw-menu-backdrop-filter)`
（`blur(40px) saturate(150%)`）让这层半透明好看。

本插件一度只借了这个填充、没借那个模糊，结果面板直接透出底下的页面——就是用户看到的
"菜单变成半透明了"。

现在要求是**写死不透**，所以面板底改用不透明、但仍然跟主题亮暗走的调色板令牌：

| 用途 | 令牌 | 浅色 / 深色 |
| --- | --- | --- |
| 面板底 / 悬浮按钮 / 提示条 | `--dsw-alias-bg-layer-1` | `#fff` / `#232324`（都完全不透明） |
| 行 hover | `--dsw-alias-interactive-bg-hover` | `#2631480f` / `#ffffff14` |
| 危险行 hover | `--dsw-alias-interactive-bg-hover-danger` | 各自配对 |
| 开关轨道（关） | `--dsw-alias-border-l3` | `#0000001f` / `#ffffff29` |
| 开关选中（开） | `--dsw-alias-brand-primary` | 每主题都有定义 |
| 开关滑杆 | `--dsw-alias-label-primary-foreground` / `--dsw-alias-switch-thumb` | 各自配对 |

`check.mjs` 有守卫断言：三个表面规则都必须用 `bg-layer-1`、都不得出现
`bg-layer-2`/`specific-menu`，且面板不得带 `backdrop-filter`（要的是硬不透明，
不是毛玻璃）。

#### 皮肤插件为什么会让它又变透明（以及可能的修法）

皮肤插件（`@linxin666/dsh-client-ui-skin-center`）通过**重定义同一批 DSH 令牌**换肤，
它连 `--dsw-alias-bg-layer-1` 一起改掉，而改成的值**带 alpha，且 alpha 随一个用户可调
的旋钮变化**。以当前启用的 `blue-fantasy` 为例：

```css
:root {
  --dsw-alias-bg-layer-1: rgba(243, 245, 251, calc(1 - var(--dsw-skin-scrim, 0) * .5));
}
body[data-ds-dark-theme] {
  --dsw-alias-bg-layer-1: rgba(26, 34, 56, calc(1 - var(--dsw-skin-scrim, 0) * .45));
}
```

`--dsw-skin-scrim` 就是皮肤设置里的"背景遮挡"，由皮肤中心**写在 `document.body` 的内联
样式**上（`document.body.style.setProperty(SCRIM_VAR, opacityValue / 100)`）。

**这里有一个反直觉的层叠细节，是本轮实测纠正的**（此前本文件写过相反的错误结论）：

- 皮肤把 `--dsw-alias-bg-layer-1` 声明在 `:root`，而外壳把**同名令牌声明在 `body`**。
- 自定义属性同样按层叠决定，且**取声明该变量的元素上的值**。本插件在 `body` 后代里
  读这个令牌，于是外壳那条（`body`，比 `:root` 更近）**胜出**，皮肤的值根本没被用到。
- 更关键的是：皮肤令牌里的 `calc(1 - var(--dsw-skin-scrim) * .5)` 在**声明它的元素
  （`:root`）上求值**，而 scrim 写在 `body` 上——`:root` 取不到，回退 `0`，所以**即使
  皮肤那条胜出，alpha 也是 1，完全不透明**。

实测（无头 Chromium，皮肤文件与会话真实配置）：

| 场景 | `--dsw-skin-scrim` 在 html / body | 读到的 `bg-layer-1` |
| --- | --- | --- |
| 浅色，外壳声明在（本机实际） | `[]` / `[0.3]` | `rgb(243, 245, 251)` → **alpha 1** |
| 浅色，剥掉外壳声明 | `[]` / `[0.3]` | `rgb(243, 245, 251)` → **alpha 1** |
| 深色，两条声明都在 | `[]` / `[0.3]` | `rgba(26, 34, 56, 0.867)` → alpha 0.867 |

也就是说：**透明度不是本插件今天面板发灰的成因**。第三行那个 `0.867` 才是"皮肤确实能
把 alpha 压下来"的证据，且它要求皮肤声明在比外壳更近的元素上、或外壳那条被移除。

同一份皮肤文件里，被改成带 alpha 的还有 `--dsw-alias-bg-base`、`-bg-layer-2/3`、
`-bg-overlay`、`-bg-module-platform`、`--dsw-alias-border-l1..l4` 等；`--dsw-specific-menu`
则被覆盖成一个**固定** 94% 不透明的值。也就是说"换一个令牌"并不能解决——同一皮肤把几乎
所有语义化背景令牌都改成了可变 alpha。

**解法（已实测并实施）**：CSS 相对颜色语法把颜色的**通道**与 **alpha** 分开，于是可以
保留令牌的颜色、强制 alpha 为 1：

```css
background: rgb(from var(--dsw-alias-bg-layer-1, <不透明兜底>) r g b / 1);
```

这样就实现了"颜色跟着主题/皮肤走，但永远 100% 不透明"——**不再依赖上面那条层叠结论
是否成立**，这正是不用去猜皮肤实现的原因。

**两个细节是实测得出的，写"顺手"的版本会静默失效**（无头 Chromium 154 实测，非推断）：

| 写法 | 计算值 | 结论 |
| --- | --- | --- |
| `rgb(from T r g b / 1)` | 完全不透明，颜色仍取 T | ✅ 正确 |
| `rgb(from T r g b)`（省略 `/ 1`） | alpha **原样继承** T 的（0.5/0.55） | ❌ 仍半透明 |
| 兜底写在**前一条** `background` | 令牌缺失时整条计算为 `rgba(0,0,0,0)` | ❌ 前一条**不是**安全网 |
| 兜底写进 `var(T, 兜底)` 内部 | 令牌缺失时用兜底色，仍不透明 | ✅ 正确 |

第 3 条尤其反直觉：令牌未定义时 `rgb(from …)` 属于"计算值阶段无效"，**不会**回退到前一条
声明，而是把背景算成全透明。所以兜底必须写在 `var()` 内部，并且外层再保留一条普通令牌声明
作为不支持该语法时的基线。

实现放在 `@supports (background: rgb(from red r g b / 1))` 内，只覆盖三个表面
（`.dshrb-menu` / `.dshrb-btn` / `.dshrb-toast`），不支持时行为与今天完全一致。
`check.mjs` 对上面四条各有一条守卫，并且都做过反向注入验证。

### 配置页的拨杆是「照抄复刻」而不是 import 官方组件

官方 `Switch` 组件在浏览器模块表里（`@deepseek-ai/dsh-client-ui-primitives`），
**`dsh-mnemon` 就是直接 `require` 它用的**。但 DSH 的插件作者指南**明文禁止**这条路：

> **不要 `require('@deepseek-ai/dsh-client-ui-primitives')`**，也不要加载任何其他
> Harness 客户端包……它们会无预警变化，纯 JS 插件没有类型检查，而且**组件一抛错就会
> 让整个槽位空白**。**改成自己写控件去匹配宿主：把 markup、CSS、行为从原件复制进
> 插件**……把复制来的类名改到你自己插件的前缀下，只保留 `--dsw-alias-*` 令牌引用，
> 并保留用户依赖的行为，例如 **`role="switch"` 配 `aria-checked`**。

（即"直接调用官方拨杆"在这个平台上是不允许的。指南给的批准做法就是复刻。）

所以这里按官方 `Switch.module.css` 的**真实数值**复刻，类名换成自己的 `dshrb-sw` /
`dshrb-swthumb`，只引用 `--dsw-alias-*` 令牌：

| 属性 | 官方值（已照抄） |
| --- | --- |
| 结构 | `<button role="switch" aria-checked>` + 真实 `<span>` 滑杆 |
| 轨道 | 36×20，`padding:2px`，`border-radius:999px` |
| 关 | `background:var(--dsw-alias-border-l3)` |
| 开 | `background:var(--dsw-alias-brand-primary)` |
| 滑杆 | 16×16，圆，`transition:transform .12s ease` |
| 滑动距离 | `translate(16px)` |
| 禁用 | `opacity:.5` |
| 状态键 | `[aria-checked=true/false]`，**不是** `:checked` |

用 `<button>` + `aria-checked` 而不是 `input[type=checkbox]`，是因为宿主控件就是
这样构建的，指南也点名 `role="switch"` 配 `aria-checked` 是要保住的行为。
`check.mjs` 逐条守卫上表（几何、两个状态令牌、滑杆尺寸与距离、禁用、状态键）。

> 曾经引用过的 `--dsw-alias-accent-fill` 和 `--dsw-alias-interactive-border-danger`
> **在 DSH 里根本不存在**，写了等于没写。改动 CSS 时请先确认令牌存在。

### 面板定位：侧栏菜单不依赖自身高度

悬浮菜单以触发按钮的**顶边**定位，`MENU_H` 仅用于防止它跑出视口底部。

侧栏菜单一度也用 `MENU_H` 估算高度再以 `top` 定位，而面板真实高度随阶段变化
（菜单阶段两行加提示，确认阶段多出标题与按钮行），估算值比实际高出约 64px，
于是面板明显偏离按钮。现在改为**以底边定位**（`bottom: <视口高 - 触发按钮顶边 + 8>`），
高度完全不参与计算：一次绘制就精确到每个阶段，既不用估算也不用二次测量。
`MENU_H` 因此只服务于悬浮菜单的视口护栏。

## 什么时候不显示

**终止模式（`dsh web`）下两个界面都不出现。** 三个硬约束叠加：

1. `dsh web` 是 stdio 应用，stdin EOF 即退出（`dsh-cmdline/lib/index.js:50`）。
   插件若 detached 拉起自身进程，新进程没有终端 stdin，会立刻自己退出。
2. 重启后端口和页面地址都可能变，而按钮所在的浏览器标签属于旧进程，无法自动跟随。
3. 复刻 `app.relaunch()` 需要拿到父级 shell 的原样启动语义，而插件碰不到父级 shell。

**「退出」在终止模式下也是多余的**：那个会话的退出就是 `Ctrl+C` 或关窗口。所以插件
回答 `supported: false`，界面整个隐藏，而不是留一个点了没用的按钮。

## 位置

位置存在浏览器 localStorage。上下边缘**故意**不作吸附目标：那里有窗口控件和输入框，
一条边会盖住两者。

## 落点是被约束逼出来的，不是选出来的

用户侧的边界（只支持 Windows、需要 WMI、会硬中断会话、重启不恢复状态、终止模式不显示）
列在 [`README.md`](../README.md#已知边界)。

这里只记**为什么落点是这两个**，因为它们看着像是随手挑的，其实每个都是唯一可行解：

- **两个界面都用官方槽位**（`sidebar.footer.action` 与 `plugins.bundle.config`），
  **不读取任何别的插件的 DOM 或样式**。
- **头像菜单里插「重启」行做不到。** 该菜单的行是硬编码数组，那个包只暴露
  `shell.overlay` / `settings.launcher` / `settings.section` /
  `settings.models.sign-in` / `shell.quota-notice`，**没有菜单行槽位**；而官方规范
  明确禁止用别人的 DOM 猜测落点。所以侧栏入口只能落在 foot 的 action 座上，
  再由 `.dshrb-sbwrap[data-dshrb-inrow]` 把它塞进头像行（见上文那一节：装了 web-all
  就加入它排出来的行，没装就由本插件补最小重排，两条互斥规则合成同一个落位）。
- **悬浮控件不挂在 dock 槽位上**：dock 是 session 作用域的，而新会话页面上没有 session，
  控件会在那里凭空消失。它是宿主全局的，所以直接挂 `document.body`。
